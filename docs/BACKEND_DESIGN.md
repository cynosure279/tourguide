# C++ 后端设计说明

接口的约定在 docs/API.md 里，这份文档讲后端内部是怎么设计实现的。

## 1. 总体结构

后端一共四层，自上而下：

```
浏览器 / 前端
    |  HTTP + JSON（/api 开头的 14 个接口）
    v
HTTP 层    server.cpp / main.cpp
    路由注册、参数检查、CORS、异常处理、静态托管
    v
存储层     graph.cpp（GraphStore）
    景点/道路的增删改查和数据校验，线程安全
    v
算法层     src/algo/ 四个文件
    DFS、拓扑排序、Dijkstra、Floyd、Prim、Kruskal
    v
模型层     model.hpp + data/hefei.json
```

分层的好处是算法层完全不知道 HTTP 的存在：它拿到的是一份只读的图，
返回的是普通的结构体，写算法的时候不用关心 JSON 怎么转、错误怎么回。
后面想换算法、改算法都不影响外面的接口。

以 GET /api/route/tour?start=0 为例，一次请求要经过：

1. httplib 的线程池接到请求，按方法 + 路径找到对应的处理函数；
2. 解析 start 参数（不传就用 id 最小的景点，不存在就报错）；
3. store.snapshot() 拷一份当前图的快照；
4. algo::buildTour 在快照上做 DFS；
5. 把结果拼成 JSON，套上 {code, msg, data} 返回；
6. 中间任何一步抛了异常，都会在统一的异常处理器里变成 JSON 错误响应。

## 2. 数据结构设计

### 2.1 图的存法

顶点放在 vector<Attraction> 里，始终保持按 id 升序。这个顺序一举三得：
/api/attractions 返回时不用再排、邻接矩阵的行列顺序就是它、找某个 id
可以二分。新景点的 id 直接取最大 id 加一。

道路放在 vector<Edge> 里，按加入的顺序存。这个顺序不能随便动：Prim
遍历边、Kruskal 排序时里程相同的边保持原顺序，都依赖它，这样算出来
的结果才和前端一致。

没有常驻的邻接矩阵或邻接表。因为景点和道路随时会增删，常驻的结构要
跟着维护，容易出不一致；直接每次用时现算（buildWeightMatrix 和
neighbors），数据量很小（几十个点），代价可以忽略，而且永远和当前
数据一致。

### 2.2 线程安全

httplib 是多线程处理请求的，而增删景点道路会改图。做法是一把互斥锁：
写操作（增删、reset）在锁内完成"检查 + 修改"；读操作通过 snapshot()
在锁内把整个图值拷一份出去，算法和 JSON 序列化都在这份快照上跑，
不占着锁。这样绝不会读到改了一半的数据，算法跑多久也不影响别的请求。

图很小，拷贝的代价可以忽略。要是图很大，可以换读写锁或者
copy-on-write，对外接口不用变。

### 2.3 数据校验

校验都集中在 GraphStore 里，失败抛 ApiError（中文消息）。主要有：

- 新增景点：代号和名称非空，代号不能重复；
- 新增道路：两端点存在、不能自环、里程大于 0（也限制不能大到离谱，
  防止多条相加溢出成无穷大）、不能和已有的边重复（无向，正反都算）；
- 删除：景点或道路不存在时报错；删景点会把相连的道路一起删掉；
- 读数据文件：字段齐全、id 不重复、坐标在 0~100、边的端点都存在、
  无自环无重边。读取失败时旧数据不受影响（先读好再整体替换）。

## 3. 算法设计

四个算法都在 src/algo/ 下，输入是只读的 Graph，输出是纯结构体。
有个贯穿始终的细节：**遍历顺序**。API.md 第 3 节要求结果是确定的，
而并列权重、邻点顺序都会影响结果，所以所有顺序都和前端
frontend/src/algo/ 里的参考实现对齐（邻点按 id 升序、并列取先遍历到的），
这样真实模式和模拟模式显示出来才是一样的。

### 3.1 导游线路（dfs.cpp）

从入口景点 DFS，邻点按 id 升序访问（neighbors() 已经排好序）。
walk 记录完整行走序列：进入一个景点记一步，从子递归退回来也记一步，
所以序列里起点会出现好几次。edges 取 walk 相邻两点组成的有向边，
按第一次出现的顺序去重，就是导游线路图。没走到的景点放 unreachable。

### 3.2 回路检测（cycle.cpp）

先拿 3.1 的导游线路图（有向图），做 Kahn 拓扑排序：入度为 0 的顶点
按 id 升序入队，出队时把邻点入度减一。入序顶点数少于总数说明有环，
没入序的顶点就是环上（或者指向环）的点。之后在剩下的子图里 DFS，
用显式栈记录当前路径，一旦走到路径上已有的顶点，从它在栈里的位置
截到栈顶就是一条环。DFS 回溯必然产生 u→v 和 v→u，所以导游线路图
正常情况下一定有环，环里的景点就是"需要人工优化"的部分。

### 3.3 最短路径（shortest.cpp）

两点间用 Dijkstra（O(n^2) 朴素写法）：每轮挑未确定里 dist 最小的点
（并列取 id 小的），松弛用严格小于；最后沿 prev 数组回溯出路径。
from 和 to 相同自然得到距离 0、路径就是它自己。

全源用 Floyd：邻接矩阵做初始值，三重循环松弛。不可达用无穷大表示，
参与加法之前先判断跳过，不然两个无穷大加起来会有溢出的风险。
矩阵里的 null 和保留两位小数都在路由层统一处理，算法层不管这些。

### 3.4 修路规划（mst.cpp）

Prim 和 Kruskal 都实现了，接口的 algo 参数选择用哪个。Prim 从 id
最小的景点出发，每轮在"树内连树外"的边里挑最短的，挑不到说明这个
连通分量连完了（图不连通时最后得到的是生成森林）。Kruskal 把边按
里程排序（用 stable_sort，里程相同的保持原顺序），配合并查集一条条
试。两种算法在默认数据上结果一致，可以互相验证。

## 4. HTTP 层

- 响应统一是 HTTP 200 + {code, msg, data}，前端只看 code 和 msg。
  业务错误（景点不存在之类）也是 200，只有访问不存在的接口才是 404。
- 路由里只管抛异常（ApiError），统一的异常处理器负责转 JSON，
  错误处理逻辑不会在每个路由里重复。
- 参数解析有两个容易踩的坑，都处理了：
  1. JSON 里超大的整数（比如 2^32）用 get<int>() 会被截断成 0，
     可能变成对真实景点的操作，所以先用 long long 接住再查范围；
  2. 路径里的 id 直接 stoi 转，超长数字会抛 out_of_range，现在先
     查范围再转，报"参数非法"而不是"内部错误"。
- CORS 全开（Access-Control-Allow-Origin: *，OPTIONS 直接 204），
  前后端分开部署也没问题；平时开发走 Vite 代理，同源用不到。
- 如果存在 frontend/dist，整个目录挂到根路径上，同时把非 /api 的
  GET 404 回退到 index.html——前端用的是 history 路由，直接刷新
  /shortest 这种地址没有回退就会 404。带扩展名的请求（静态资源）
  不回退，保持 404。

## 5. 构建与运行

CMake + C++17，两个依赖都是头文件库放在 third_party/ 里，任何机器
clone 下来 cmake --build 就能编。CMakeLists 里把项目根目录的绝对
路径编译进了二进制（TOUR_PROJECT_ROOT 宏），运行时靠它找
data/hefei.json 和 frontend/dist，从哪个目录启动都没问题；也可以在
命令行参数里直接指定数据文件。

## 6. 测试

- scripts/smoke.sh 把 14 个接口都请求一遍，包括一些故意报错的用例；
- 和前端模拟模式对过：同一份数据改动下，每个算法接口的结果和 JS
  参考实现逐个对比，全部一致（包括不连通、删景点级联删边这些情况）；
- 试过空图、单景点、起终点相同、不可达这些边界；
- 并发压过一把：几十个请求同时读写，全部正常。
